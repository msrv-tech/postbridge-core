# Internationalization

`postbridge-core` now includes a shared i18n layer intended to serve bot adapters, API error surfaces, and future web cabinets.

## Goals

- keep English as the canonical base locale in `core`
- support multiple product languages without branching product logic
- let hosted deployments add their own text and translations later
- make self-hosted web surfaces reuse the same message keys

## Current scope

Phase 1 is implemented for the Telegram bot runtime:

- bundled locales: `en`, `ru`
- Telegram bot text is stored as message keys, not inline strings
- unified API error payloads localize `message` through the same catalog
- the built-in `/web` surface now uses the same Core-wide locale contract

The next migration targets should be:

- web cabinet text
- email and notification templates

## File layout

```text
src/postbridge/i18n/
  __init__.py
  models.py
  service.py
  locales/
    en.json
    ru.json
```

## Contract

The core contract is:

- stable message keys
- locale-specific string catalogs
- runtime interpolation with `{{param}}`
- one Core-wide configured default locale
- fallback to `en` if the configured locale is unsupported

Example keys:

- `bot.start.saas_intro`
  Platform-specific onboarding copy must stay inside the platform namespace. Do not mix Telegram onboarding with MAX or other platform guidance in the same message.
- `bot.channel.connected`
- `bot.auth.invalid_or_expired_link`

## Runtime API

```python
from postbridge.i18n import get_i18n

i18n = get_i18n()

locale = i18n.resolve_locale(
    explicit=None,
    user_locale=None,
    platform_locale="ru-RU",
    accept_language=None,
).locale

text = i18n.translate(
    "bot.channel.connected",
    locale=locale,
    params={"title": "News"},
)
```

In `postbridge-core`, the active locale is configured once for the whole runtime:

- `POSTBRIDGE_DEFAULT_LOCALE=en|ru|...`

Current Core behavior is intentionally simple:

- one locale applies to the whole deployment
- bots, API surfaces, and future self-hosted web surfaces should all use that same locale
- if the configured locale is unsupported, Core falls back to `en`

The locale resolver still supports richer precedence for future SaaS overlays, but Core itself should be treated as a single-locale deployment.

## Translation catalogs

Catalogs are simple JSON dictionaries:

```json
{
  "bot.button.open_web": "Open web",
  "bot.channel.connected": "Channel \"{{title}}\" is connected."
}
```

Guidelines:

- use namespaced keys
- never use source text as a key
- keep placeholders stable across locales
- keep machine-readable status codes outside the translation layer

## Hosted Overlay Model

Hosted deployments should not fork this system. They can add an overlay catalog with the same key format and fallback behavior:

1. look up a key in hosted deployment locale catalogs
2. if missing, fall back to `postbridge-core` locale catalogs
3. if still missing, fall back to `postbridge-core` English

This keeps shared product language in Core while allowing deployment-specific wording outside the public repository.

## API evolution

For user-facing API errors and notifications, prefer payloads shaped like:

```json
{
  "code": "invalid_or_expired_link",
  "message_key": "error.auth.invalid_or_expired_link",
  "params": {},
  "message": "This link is expired or already used."
}
```

That allows bots, web clients, and future platform adapters to localize the same semantic error consistently.
